# 직렬화 (Serialization)

## 핵심 개념

- **직렬화**: 메모리 안의 객체를 **저장하거나 전송할 수 있는 형태**(문자열, 바이트 열)로 바꾸는 것
- **역직렬화(Deserialization)**: 그 형태를 다시 메모리 안의 객체로 되살리는 것
- 메모리 속 객체는 **주소로 서로 연결된 구조**임. 이 주소는 프로그램 밖에서는 의미가 없음
- 그래서 저장하거나 보내려면 연결 구조를 **한 줄로 펼쳐서 값만으로** 표현해야 함. "직렬(serial)"이라는 이름이 여기서 나옴

```mermaid
graph LR
    A["메모리 속 객체<br/>참조로 연결된 구조"] -->|직렬화| B["JSON · 바이너리"]
    B --> C["파일 저장<br/>네트워크 전송"]
    C -->|역직렬화| D["새 객체로 복원"]
```

## 저장되는 것과 안 되는 것

- 직렬화는 **데이터(상태)만** 다룸. 메서드, 즉 동작은 저장되지 않음
- 어떤 멤버를 데이터로 볼지는 **직렬화기마다 규칙이 다름**
  - public 필드만 보는 것, 프로퍼티까지 보는 것, `[SerializeField]` 같은 표시가 붙은 private 필드까지 보는 것 등
- 직렬화기는 대부분 [[Reflection]]으로 타입의 멤버를 훑어서 무엇을 저장할지 결정함
- **직렬화 여부는 변수의 선언(접근 제한자, 어트리뷰트, 타입)으로 정해짐**. 그 변수를 어디서 어떻게 쓰는지와는 무관함

## 형식 비교

| 형식 | 장점 | 단점 | 용도 |
| --- | --- | --- | --- |
| JSON | 사람이 읽을 수 있음. 디버깅 쉬움 | 크기가 큼. 파싱이 느림 | 설정, 세이브 파일, 웹 API |
| XML | 구조 표현이 풍부함 | JSON보다 더 장황함 | 레거시 시스템 |
| 바이너리 | 작고 빠름 | 사람이 못 읽음. 버전 변경에 약함 | 대용량 데이터, 네트워크 |
| MessagePack, Protobuf | 작고 빠르면서 스키마 관리 가능 | 별도 라이브러리 필요 | 게임 서버 통신 |

## C#의 직렬화 도구

| 도구 | 특징 |
| --- | --- |
| `System.Text.Json` | .NET 표준 JSON 직렬화기 |
| Newtonsoft.Json (Json.NET) | 기능이 많아 유니티 프로젝트에서도 널리 쓰임 |
| `JsonUtility` | 유니티 내장. 빠르지만 유니티 직렬화 규칙을 그대로 따름 |
| `BinaryFormatter` | **보안 문제로 사용이 중단됨.** 쓰면 안 됨 |

- `[Serializable]` 어트리뷰트는 "이 타입은 직렬화해도 된다"는 표시임. 요구하는 직렬화기도 있고 무시하는 직렬화기도 있음
- `BinaryFormatter`는 역직렬화할 때 데이터 안에 적힌 타입을 그대로 만들어 실행할 수 있어, 조작된 파일 하나로 임의 코드가 실행될 수 있었음

## 주의할 점

**참조 공유가 풀림**

- 두 변수가 **같은 객체**를 가리키던 구조를 직렬화하면, 역직렬화 후에는 **서로 다른 두 객체**로 복원되는 경우가 많음
- 같은 객체였다는 사실이 저장되지 않기 때문임

**순환 참조**

- A가 B를, B가 A를 참조하면 직렬화가 끝없이 반복되거나 에러가 남
- 직렬화기마다 막는 설정이 있지만, 구조 자체를 피하는 것이 안전함

**다형성 정보가 사라짐**

- 부모 타입 변수에 자식 객체가 들어 있어도, 부모 타입 기준으로 저장되면 자식의 데이터와 타입 정보가 사라짐
- 타입 정보를 함께 저장하는 옵션이나 별도 처리가 필요함

**버전 호환**

- 저장 후 필드 이름을 바꾸거나 지우면, 예전 세이브 파일을 읽을 때 값이 사라지거나 실패함
- 데이터에 **버전 번호**를 함께 저장해 두면 구버전 데이터를 변환하는 처리를 넣을 수 있음

## 유니티 직렬화

- 유니티는 인스펙터 표시, 씬·프리팹·에셋 저장을 위해 **별도의 직렬화 시스템**을 가짐
- `JsonUtility`도 이 규칙을 따름

| 대상 | 직렬화 여부 |
| --- | --- |
| public 필드 | 됨 |
| private 필드 + `[SerializeField]` | 됨 |
| private 필드 (표시 없음) | **안 됨** |
| 프로퍼티 | 안 됨 |
| static 필드 | 안 됨 |
| `Dictionary` | 안 됨 |
| `[Serializable]`이 붙은 일반 클래스·구조체 | 됨 (필드 안쪽까지 같은 규칙) |
| 다형성 필드 | 기본은 안 됨. `[SerializeReference]` 필요 |

- 인스펙터에 값이 안 보이거나 플레이 후 값이 날아간다면 대부분 이 규칙에 걸린 것임
- 자세한 내용은 [[Unity Serialization]]에서 다룸

## 게임 개발 관점에서

**세이브 시스템의 핵심**

- 게임 진행 상태를 데이터 클래스로 모으고, 직렬화해서 파일로 저장함
- 저장용 데이터 클래스는 게임 로직 객체와 분리해 두면 버전 관리와 변환이 쉬워짐

**세이브 파일 조작**

- JSON은 메모장으로 열어 골드 수치를 바꿀 수 있음
- 싱글 게임이라면 크게 문제 되지 않지만, 경쟁 요소가 있다면 암호화나 체크섬으로 변조를 감지해야 함
- 근본적으로 중요한 데이터는 클라이언트가 아니라 서버가 가지고 있어야 함

**네트워크 통신**

- 서버와 주고받는 모든 데이터가 직렬화를 거침
- 패킷 크기가 곧 통신량과 지연이라, 실시간 게임은 JSON보다 바이너리 형식을 선호함

## 의문점 / 더 알아볼 것

- `ISerializationCallbackReceiver` — 유니티에서 Dictionary를 직렬화하는 우회 방법
- 직렬화기가 private 필드를 읽고 쓰는 방식과 리플렉션 비용
- 소스 제너레이터 기반 직렬화 — 리플렉션 없이 빠르게 직렬화하는 최신 방식
- IL2CPP 빌드에서 직렬화 대상 타입이 코드 스트리핑으로 사라지는 문제
- 세이브 데이터 마이그레이션 설계
