# 부호 없는 정수 (Unsigned Integer)

## 핵심 개념

- **부호 없는 정수**: 0과 양수만 표현하는 정수 타입
- 부호에 쓰던 비트까지 값에 쓰므로, 같은 크기의 부호 있는 타입보다 **양수 범위가 2배**임

| 키워드 | .NET 타입 | 크기 | 범위 |
| --- | --- | --- | --- |
| `byte` | `Byte` | 1바이트 | 0 ~ 255 |
| `ushort` | `UInt16` | 2바이트 | 0 ~ 65,535 |
| `uint` | `UInt32` | 4바이트 | 0 ~ 약 43억 |
| `ulong` | `UInt64` | 8바이트 | 0 ~ 약 1844경 |

- 이름 규칙이 비대칭임. 1바이트만 **`byte`가 부호 없는 쪽**이고 `sbyte`가 부호 있는 쪽임. 나머지는 `u`가 붙은 쪽이 부호 없음

## 언더플로

- 0에서 1을 빼면 음수가 되지 않고 **최댓값으로 넘어감**

```
uint 0 - 1  →  4,294,967,295
```

**대표적인 함정 — 거꾸로 도는 반복문**

- 부호 없는 변수로 큰 수에서 0까지 내려가는 반복문을 짜면 `i >= 0` 조건이 **항상 참**이 됨
- 0 다음에 최댓값으로 넘어가기 때문에 반복이 끝나지 않음
- "음수가 될 수 없으니 안전하겠지"라는 생각과 정반대로 동작하는 지점임

## 부호 있는 타입과 섞을 때

- `int`와 `uint`를 함께 연산하면 결과가 **`long`**으로 승격됨. 둘 다를 담을 수 있는 타입이 필요하기 때문임
- `ulong`과 부호 있는 타입은 섞어 쓸 수 없어 컴파일 에러가 남
- 비교할 때도 한쪽을 캐스팅해야 해서 코드가 지저분해짐

## C#에서 잘 안 쓰는 이유

- .NET API 대부분이 `int`를 씀. `List.Count`, `Array.Length` 모두 `int`임
- 부호 없는 타입으로 받으면 이런 값들과 섞을 때마다 캐스팅이 필요함
- `byte`를 제외한 부호 없는 타입은 다른 .NET 언어와의 호환 규칙(CLS)을 만족하지 않음
- "음수가 될 수 없다"는 의도를 표현하려고 쓰기 쉽지만, 실제로는 언더플로가 음수보다 **발견하기 더 어려운 버그**를 만듦

## 그래도 쓰는 곳

| 타입 | 용도 |
| --- | --- |
| `byte` | 파일, 패킷, 이미지 같은 바이너리 데이터. 색상 채널 (0~255) |
| `uint`, `ulong` | 해시값, 비트마스크, 고유 ID |

**비트 연산에서 유리함**

- 부호 있는 타입을 오른쪽으로 시프트하면 빈자리를 **부호 비트로 채움** (산술 시프트)
- 부호 없는 타입은 **0으로 채움** (논리 시프트)
- 비트를 순수한 비트로 다룰 때는 부호 없는 타입이 예측대로 동작함

## 게임 개발 관점에서

**색상은 byte로 다룸**

- 유니티의 `Color32`는 RGBA 각 채널을 `byte`(0~255)로 가짐
- `Color`(float 0~1)보다 메모리가 4분의 1이라 픽셀을 대량으로 다룰 때 쓰임

**네트워크와 저장**

- 패킷과 세이브 파일은 결국 `byte` 배열로 주고받음
- 범위가 작은 값을 `byte`나 `ushort`로 담아 전송량을 줄임

**게임 로직에는 int가 기본**

- 체력, 개수처럼 "음수가 안 되는 값"이라도 `int`로 두고, 0 아래로 내려가지 않게 로직에서 막는 편이 안전함
- 부호 없는 타입은 언더플로 순간 엄청나게 큰 값이 되어 체력이 최대치로 튀는 식의 버그를 만듦

## 의문점 / 더 알아볼 것

- C# 11의 `>>>` 연산자 — 부호 있는 타입에서도 논리 시프트를 하는 방법
- CLS 호환(CLS Compliance)이 무엇이고 왜 부호 없는 타입이 빠졌는가
- 유니티 `LayerMask`가 `uint`가 아니라 `int`인 이유
- `Span<byte>`, `BitConverter`로 바이트 배열을 다루는 방법
- 짝을 이루는 [[Signed Integer]], 바탕 개념인 [[Bit & Byte]]
