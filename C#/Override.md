# override 키워드 (Override)

## 핵심 개념

- **`override`**: 부모 클래스가 재정의를 허락한 멤버를 **자식 클래스가 새로 정의**하는 키워드
- 재정의하면 부모 타입 변수로 호출해도 **자식의 구현이 실행됨**
- 부모가 허락(`virtual`, `abstract`)해야만 쓸 수 있음. 허락하는 쪽의 설명은 [[Virtual]] 참고

## 재정의할 수 있는 조건

| 부모 멤버                     | override 가능?                    |
| ----------------------------- | --------------------------------- |
| `virtual`                     | 가능                              |
| `abstract`                    | 가능 (반드시 해야 함)             |
| `override` (이미 재정의된 것) | 가능 — 더 아래 자식이 다시 재정의 |
| `sealed override`             | **불가**                          |
| 아무 표시 없음                | **불가**                          |
| `static`                      | **불가**                          |

## 지켜야 할 규칙

| 규칙             | 내용                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 시그니처 일치    | 이름, 매개변수 구성이 부모와 같아야 함                                         |
| 접근 제한자 유지 | 부모가 `protected`면 자식도 `protected`. 넓히거나 좁힐 수 없음                 |
| 반환 타입        | 원칙적으로 같아야 함. C# 9부터는 더 구체적인 타입으로 좁힐 수 있음 (공변 반환) |
| 정적 불가        | `static` 멤버는 객체에 속하지 않아 재정의 개념이 없음                          |

- 매개변수가 하나라도 다르면 재정의가 아니라 **오버로딩**이 됨. [[Overloading]] 참고

## base — 부모 구현 이어 쓰기

- 재정의한 메서드 안에서 `base`로 **부모의 원래 구현을 호출**할 수 있음
- 부모 동작을 **대체**할지, 부모 동작에 **덧붙일지**에 따라 호출 여부를 정함

| 방식                             | 의미                                     |
| -------------------------------- | ---------------------------------------- |
| `base`를 부르지 않음             | 부모 동작을 완전히 대체함                |
| `base`를 먼저 부르고 이어서 처리 | 부모 동작 뒤에 추가 동작을 붙임          |
| 처리 후 마지막에 `base` 호출     | 추가 동작을 먼저 하고 부모 동작을 실행함 |

- 부모가 초기화나 정리를 하는 메서드라면 `base`를 빼먹으면 그 처리가 사라짐. 의도한 것인지 확인할 것

## sealed override — 여기서 멈춤

- 재정의하면서 `sealed`를 함께 붙이면, **더 아래 자식은 이 멤버를 다시 재정의할 수 없음**
- 이 단계의 구현이 바뀌면 안 되는 경우에 씀

## object의 메서드 재정의

- 모든 클래스는 `object`를 상속하므로, `object`가 가진 재정의 가능한 메서드를 재정의할 수 있음

| 메서드        | 재정의하는 이유                                         |
| ------------- | ------------------------------------------------------- |
| `ToString`    | 디버그 출력이나 로그에 객체 내용을 읽기 좋게 보여주려고 |
| `Equals`      | "같은 객체인가"가 아니라 "내용이 같은가"로 비교하려고   |
| `GetHashCode` | `Equals`와 짝을 맞추려고                                |

**Equals와 GetHashCode는 반드시 함께**

- `Equals`만 재정의하고 `GetHashCode`를 그대로 두면, `Dictionary`나 `HashSet`에서 같은 내용의 객체를 찾지 못함
- 해시 기반 컬렉션은 먼저 해시값으로 칸을 찾고 그다음 `Equals`로 비교하기 때문임
- 규칙: **`Equals`가 같다고 판단하는 두 객체는 해시값도 같아야 함**
- 컴파일러도 하나만 재정의하면 경고를 줌. [[KeyValuePair]]의 같음 비교 문제와 같은 맥락임

## 프로퍼티 재정의

- 프로퍼티도 `virtual`이면 재정의할 수 있음
- 부모가 정한 접근자(읽기, 쓰기)의 범위 안에서만 재정의 가능함. 부모에 없는 접근자를 새로 추가할 수는 없음

## 게임 개발 관점에서

**유니티 메시지 메서드 재정의 패턴**

- `Awake`, `Start`, `Update` 같은 메서드는 원래 재정의 대상이 아니라 유니티가 이름으로 찾아 부름
- 상속 구조에서 부모의 초기화가 빠지지 않게 하려면, 부모에서 `protected virtual`로 선언하고 자식에서 `override`한 뒤 `base`를 부르는 방식을 씀. [[Virtual]] 참고

**공통 동작을 부모에, 차이를 자식에**

- 적 공통 부모가 "피격 처리"를 가지고, 특정 적만 재정의해서 추가 반응(분열, 반격 등)을 붙이는 식으로 씀
- 재정의할 때 부모가 보장하던 동작을 깨지 않도록 주의할 것. [[Liskov Substitution Principle]] 참고

**디버그용 ToString**

- 데이터 클래스나 구조체에 `ToString`을 재정의해 두면, 로그나 디버거에서 내용을 바로 확인할 수 있어 디버깅이 훨씬 편해짐

## 의문점 / 더 알아볼 것

- 공변 반환 타입의 세부 규칙과 유니티 지원 여부
- `abstract` 메서드를 재정의하지 않으면 생기는 일 — 자식도 추상 클래스가 되어야 함
- 같음 비교를 제대로 구현하는 방법 — `IEquatable<T>`, 연산자 오버로딩과의 일관성
- 재정의된 메서드를 리플렉션으로 구분하는 방법
- 관련 노트 — [[Inheritance]], [[Polymorphism]], [[New]]
