# 2차원 배열 (2D Array)

## 핵심 개념

- 행과 열로 이루어진 **격자 형태**의 데이터를 담는 배열
- C#에는 2차원 데이터를 담는 방법이 두 가지 있음
  - **다차원 배열** `[,]` — 하나의 직사각형 덩어리
  - **가변 배열** `[][]` — 배열을 요소로 가지는 배열
- 기본적인 배열의 성질은 [[Array]] 참고

## 두 방식 비교

| 구분 | 다차원 배열 `[,]` | 가변 배열 `[][]` |
| --- | --- | --- |
| 구조 | 하나의 덩어리 | 바깥 배열 + 행마다 따로 만든 배열 |
| 행 길이 | 모두 같음 (직사각형) | 행마다 다를 수 있음 |
| 할당 | 한 번 | 바깥 배열 1번 + 행 수만큼 |
| 접근 문법 | `grid[y, x]` | `grid[y][x]` |
| 전체 크기 | `Length`가 **전체 요소 수** | `Length`가 **행 수** |
| 각 차원의 길이 | `GetLength(0)`, `GetLength(1)` | `grid.Length`, `grid[y].Length` |

## 메모리 배치

```
다차원 배열 int[3, 4]  — 한 덩어리, 행 단위로 이어짐
┌────────────┬────────────┬────────────┐
│ 0행 4칸     │ 1행 4칸     │ 2행 4칸     │
└────────────┴────────────┴────────────┘

가변 배열 int[3][]  — 행마다 따로 할당
┌──────┐
│ 주소 │──▶ [ 0행 4칸 ]
│ 주소 │──▶ [ 1행 2칸 ]      ← 길이가 달라도 됨
│ 주소 │──▶ [ 2행 5칸 ]
└──────┘
```

- C#의 다차원 배열은 **행 단위로 연속 저장**됨 (행 우선, Row-major)
- 그래서 순회할 때 **바깥 반복을 행, 안쪽 반복을 열**로 돌아야 메모리를 순서대로 읽음
- 반대로 돌면 매번 한 행씩 건너뛰며 읽게 되어 CPU 캐시를 잘 쓰지 못하고 느려짐

## 자주 걸리는 함정

**`Length`의 의미가 다름**

- 다차원 배열의 `Length`는 행 × 열, 즉 **전체 요소 수**임
- 행 수나 열 수가 필요하면 `GetLength(차원 번호)`를 써야 함

**가변 배열의 행은 비어 있음**

- 가변 배열은 바깥 배열만 만들면 각 행이 **`null`**인 상태임
- 행마다 따로 배열을 만들어 넣지 않고 접근하면 `NullReferenceException`이 남

**행·열과 x·y의 순서 혼동**

- 배열은 보통 `[행, 열]`로 쓰는데, 게임 좌표는 `(x, y)` 순서라 둘이 뒤집힘
  - 행 = y (세로), 열 = x (가로)
- `[x, y]`로 쓸지 `[y, x]`로 쓸지 **프로젝트 안에서 하나로 정해야** 함
- 섞이면 가로세로가 뒤바뀐 맵이 나오거나, 정사각형이 아닌 맵에서 범위 초과 예외가 남

**경계 확인**

- 이웃 칸을 볼 때 맵 가장자리에서는 범위를 벗어남
- 접근 전에 "이 좌표가 맵 안인가"를 확인하는 처리를 한곳에 두면 실수가 줄어듦

## 1차원 배열로 펼치기

- 2차원 데이터를 **1차원 배열 하나**에 담고 위치를 계산하는 방식도 많이 씀

| 변환 | 계산 |
| --- | --- |
| (x, y) → 인덱스 | `y × 가로 + x` |
| 인덱스 → x | `인덱스 % 가로` |
| 인덱스 → y | `인덱스 / 가로` |

- 메모리가 완전히 연속이고 할당이 한 번뿐임
- 일반적으로 다차원 배열보다 접근이 빠른 편임
- 대신 가로 길이를 함께 들고 다녀야 하고, 계산식이 코드 곳곳에 퍼지지 않게 한곳에 모아둬야 함

## 게임 개발 관점에서

**인스펙터에 직렬화되지 않음**

- 유니티는 **다차원 배열과 가변 배열을 직렬화하지 않음**. 인스펙터에 안 보이고 값이 저장되지 않음
- 인스펙터에서 편집해야 한다면 다음 방법을 씀
  - 1차원 배열 + 가로 길이로 저장
  - 한 행을 `[Serializable]` 클래스로 감싸고, 그 클래스의 배열을 둠
- 직렬화 규칙은 [[Serialization]] 참고

**격자 데이터의 기본 자료구조**

- 타일 맵 데이터, 인벤토리 칸, 퍼즐 판(매치3 등), 길찾기용 격자처럼 크기가 정해진 격자에 잘 맞음
- 좌표로 바로 칸에 접근할 수 있어 "이 위치에 무엇이 있나"를 빠르게 확인함

**이웃 탐색**

- 상하좌우(또는 8방향) 이웃을 살필 때는 방향별 x, y 변화량을 작은 배열로 만들어 두고 반복하는 방식이 깔끔함
- 맵 가장자리 경계 확인과 함께 써야 함

**유니티 타일맵과의 관계**

- 화면에 그리는 것은 [[TileMap]]이 맡고, 게임 로직용 데이터(이동 가능 여부, 비용 등)는 2차원 배열로 따로 들고 있는 구성이 흔함

## 의문점 / 더 알아볼 것

- 3차원 이상 배열과 복셀 데이터
- 다차원 배열 접근이 느린 이유 — 경계 검사와 위치 계산 방식
- CPU 캐시 라인과 순회 순서가 성능에 미치는 영향
- 희소한 격자(대부분 비어 있는 맵)를 Dictionary로 다루는 방법
- 그리드 기반 길찾기 — BFS, A*
